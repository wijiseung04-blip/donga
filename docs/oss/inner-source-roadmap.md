# Inner Source 도입 로드맵

오픈소스 협업 방식(공개된 코드, PR, 코드 리뷰, 자발적 기여)을 조직 내부에 적용하기 위한 계획입니다.
관련 문서: [라이선스 비교 분석](license-analysis.md), [CONTRIBUTING.md](../../CONTRIBUTING.md)

## 1. 대상 조직과 현재 문제 (가상 시나리오)

| 항목 | 내용 |
|---|---|
| 조직 | 웹 서비스 3개를 운영하는 IT 회사 개발본부 (팀 3개, 개발자 약 20명) |
| 현재 방식 | 팀마다 저장소를 비공개로 운영. 다른 팀 코드는 볼 수 없음 |
| 문제 1: 중복 개발 | 로그인·회원 관리, 알림 발송 기능을 세 팀이 각자 구현 |
| 문제 2: 품질 편차 | 보안 패치가 한 팀에만 적용되고 나머지 팀은 모름 |
| 문제 3: 사일로 | 팀 간 질문은 개인 메신저로 오가서 기록이 남지 않음 |

## 2. 기대 효과와 도전 과제

| 기대 효과 | 근거 |
|---|---|
| 중복 개발 감소 | 공통 모듈을 한 곳에서 관리하고 모든 팀이 재사용 |
| 품질 향상 | 여러 팀의 코드 리뷰로 버그·보안 문제를 조기 발견 |
| 지식 공유 | 이슈·PR·위키에 논의가 남아 신규 입사자 온보딩이 빨라짐 |
| 인재 성장 | 다른 팀 프로젝트에 기여하며 기술 역량과 시야가 넓어짐 |

| 도전 과제 | 해결책 |
|---|---|
| "내 팀 코드를 왜 남이 고치나"라는 소유권 의식 | 모듈마다 메인테이너 팀을 두고 CODEOWNERS로 최종 승인권을 보장 |
| 다른 팀 기여에 쓸 시간이 없음 | 업무 시간의 10%를 Inner Source 기여 시간으로 공식 인정 |
| 외부 기여 PR의 품질이 들쭉날쭉 | CONTRIBUTING·PR 템플릿·CI(테스트, 린트)로 기준을 자동 검증 |
| 공개 범위에 대한 보안 우려 | 저장소는 조직 내부 공개(Internal)로만 설정, Secret 스캔·의존성 스캔 필수 |

## 3. 단계별 실행 로드맵

### 1단계: 준비 (1~2개월)
- **문화**: 경영진 후원 확보, 전체 공유회에서 Inner Source 목적 설명
- **도구**: GitHub 조직 정비, 공통 모듈 저장소를 Internal로 생성
- **정책**: 기여 프로세스(CONTRIBUTING, 이슈·PR 템플릿, Conventional Commits) 표준 확정
- **산출물**: Inner Source 가이드라인 문서, 파일럿 대상 선정

### 2단계: 파일럿 (3~4개월)
- **대상**: 세 팀이 중복 개발한 **로그인·회원 관리 모듈**을 하나로 통합
- **운영**: A팀이 메인테이너, B·C팀은 기여자로 PR 제출
- **도구**: CI로 테스트·린트 자동 검증, 사내 패키지 레지스트리(GitHub Packages)로 배포
- **점검**: 매월 회고에서 리뷰 대기 시간, 기여 장벽을 확인하고 가이드 수정

### 3단계: 확산 (5~8개월)
- 알림 발송, 공통 UI 컴포넌트 등 추가 모듈을 Inner Source로 전환
- 팀마다 "Trusted Committer"(다른 팀 PR을 리뷰하는 담당자) 1명 지정
- 사내 위키에 모듈 목록과 사용법을 모은 카탈로그 구축

### 4단계: 정착 (9~12개월)
- 신규 공통 기능은 Inner Source로 시작하는 것을 기본 원칙으로 채택
- 기여 실적을 인사 평가에 반영
- 분기마다 KPI를 검토하고 로드맵 갱신

## 4. 3대 핵심 정책

| 정책 | 내용 |
|---|---|
| 기여 프로세스 | 이슈·PR 템플릿, 브랜치 전략 표준화(`feature/*`, `fix/*`), Conventional Commits |
| 코드 리뷰 기준 | CODEOWNERS로 필수 리뷰어 지정, 승인 1건 이상, CI 통과, 테스트 커버리지 70% 이상 |
| 라이선스·보안 | 내부 코드 사용 정책 수립, 의존성 라이선스 검사(GPL 코드 유입 방지), Secret 스캔·의존성 취약점 스캔 |

## 5. 인센티브

- 업무 시간의 10%를 다른 팀 기여 시간으로 인정
- 분기별 "Top Contributor" 선정과 공유회 발표 기회
- 기여 실적(머지된 PR, 리뷰 수)을 인사 평가 항목에 반영
- 메인테이너 팀에는 모듈 사용 현황을 성과로 인정

## 6. 성과 지표 (KPI)

| 지표 | 측정 방법 | 현재 (가정) | 1년 목표 |
|---|---|---|---|
| 공통 모듈 재사용률 | 공통 모듈을 사용하는 서비스 수 / 전체 서비스 수 | 0% | 100% (3/3) |
| 팀 간 기여 PR 비율 | 다른 팀이 제출한 PR / 공통 모듈 전체 PR | 0% | 30% 이상 |
| 기여자 수 | 공통 모듈에 PR이 머지된 개발자 수 | 0명 | 10명 이상 |
| 첫 리뷰까지 걸리는 시간 | PR 생성부터 첫 리뷰까지 중앙값 | - | 1영업일 이내 |
| 중복 코드 감소 | 같은 기능을 따로 구현한 팀 수 | 3팀 | 1팀 (메인테이너만) |
| 보안 패치 전파 시간 | 패치 머지부터 전 서비스 반영까지 | 측정 불가 | 1주 이내 |

## 7. 이 저장소에 이미 적용한 Inner Source 요소

donga는 1인 저장소지만, 위 정책을 작은 규모로 미리 적용해 두었다.

| 요소 | 적용 내용 |
|---|---|
| 기여 프로세스 | [CONTRIBUTING.md](../../CONTRIBUTING.md), PR·이슈 템플릿, Conventional Commits |
| 코드 리뷰 | [리뷰 가이드](../REVIEW_GUIDE.md)의 `[MUST]`/`[SHOULD]` 태그, CODEOWNERS |
| 자동화 | Python 매트릭스 CI, 자동 응답, SLA 추적, 주간 요약 워크플로 |
| 지식 공유 | Wiki, [ADR](../adr/README.md), Discussions의 RFC |
