# Code Review Guide

리뷰의 목적은 결함을 줄이고, 지식을 공유하고, 코드베이스의 일관성을 지키는 것입니다. 사람이 아니라 코드를 리뷰합니다.

## 1. 코멘트 태그

모든 리뷰 코멘트는 맨 앞에 태그를 붙여 **중요도**를 분명히 합니다.

| 태그 | 의미 | 머지 전 처리 |
|---|---|---|
| `[MUST]` | 버그, 보안 문제, 테스트 누락, 규칙 위반 등 반드시 고쳐야 하는 사항 | **필수**. 해결 전까지 머지 불가 |
| `[SHOULD]` | 강하게 권장하는 개선. 가독성, 유지보수성, 더 나은 설계 | 반영하거나, 반영하지 않는 이유를 답글로 남김 |
| `[COULD]` | 선택 사항. 사소한 취향이나 아이디어 | 작성자 재량 |
| `[QUESTION]` | 의도를 확인하기 위한 질문 | 답변 필요 |
| `[PRAISE]` | 잘한 점 공유 | 없음 |

### 코멘트 작성 형식

```
[MUST] 무엇이 문제인지 한 문장

- 왜: 이 문제가 일으키는 결과 (실패 시나리오)
- 제안: 구체적인 수정 방법 또는 코드
```

예시:

```
[MUST] 빈 문자열이 들어오면 "Hello, !"가 반환됩니다.

- 왜: 호출부에서 사용자 입력을 그대로 넘기면 잘못된 인사말이 노출됩니다.
- 제안: `if not name.strip(): raise ValueError(...)`로 검증하고 테스트를 추가해 주세요.
```

```
[SHOULD] 매직 넘버 127 대신 상수 MAX_LINE_LENGTH로 분리하면 의도가 드러납니다.
```

## 2. 리뷰 결과(Review event) 선택

| 상황 | 선택 |
|---|---|
| `[MUST]`가 하나 이상 있음 | **Request changes** |
| `[SHOULD]` 이하만 있음 | **Approve** (코멘트 포함) 또는 **Comment** |
| 질문만 있음 | **Comment** |

## 3. 리뷰어 체크리스트

- [ ] **정확성**: 의도대로 동작하는가? 경계값/예외 상황은?
- [ ] **테스트**: 변경을 검증하는 테스트가 있고 CI가 통과하는가?
- [ ] **범위**: PR이 하나의 목적에 집중되어 있는가?
- [ ] **가독성**: 이름과 구조만으로 의도가 읽히는가?
- [ ] **보안**: 토큰/비밀번호 노출, 과도한 워크플로 권한은 없는가?
- [ ] **규칙**: 브랜치 이름, Conventional Commits, PR 템플릿을 지켰는가?
- [ ] **문서**: 사용법이 바뀌었다면 문서가 갱신되었는가?

## 4. 작성자 가이드

- PR 설명에 "무엇을, 왜"를 적고, 리뷰 포인트를 명시합니다.
- 리뷰 코멘트에는 반영 커밋 링크나 이유로 답하고, 반영이 끝난 스레드는 **Resolve** 합니다.
- `[MUST]` 반영은 별도 커밋(`fix: 리뷰 반영 - ...`)으로 올려 재리뷰가 쉽도록 합니다.

## 5. 응답 시간 (협업 시)

- 리뷰 요청 후 **1영업일 이내** 첫 리뷰를 남깁니다.
- 작성자는 리뷰 후 **1영업일 이내** 응답합니다.

## 6. 1인 운영 시 셀프 리뷰

혼자 운영하는 동안에도 같은 태그와 절차로 리뷰를 남깁니다. 리뷰 기록이 곧 변경 이유의 문서가 됩니다.

1. PR을 연 뒤 **Files changed** 화면에서 리뷰어 입장으로 diff를 다시 읽습니다. 작성 직후보다 시간을 두고 보는 것이 효과적입니다.
2. 3장 체크리스트를 기준으로 줄 단위 코멘트에 `[MUST]`/`[SHOULD]` 태그를 붙입니다.
3. GitHub는 본인 PR에 Approve/Request changes를 허용하지 않으므로 **Comment**로 제출합니다. 리뷰 본문에 태그별 건수 표와 "가이드 기준 판정: Request changes/Approve"를 적습니다.
4. `[MUST]`는 반영 커밋을 올리고, 스레드에 커밋 해시로 답한 뒤 **Resolve** 합니다. 브랜치 보호의 *conversation resolution* 규칙이 미해결 스레드가 남은 머지를 막습니다.
5. CI가 통과하면 머지합니다.
